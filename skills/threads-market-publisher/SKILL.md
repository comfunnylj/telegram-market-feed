# Threads Market Brief Publisher

## 목적
Telegram 증권정보 대시보드의 최신 데이터를 바탕으로 웹에서 추가 검증·보강한 뒤, Threads용 장문 시장 브리핑과 이미지 1장을 생성해 Metricool을 통해 자동 게시한다.

## 데이터 소스
매 실행마다 아래 공개 GitHub 저장소의 최신 파일을 읽는다.
- https://raw.githubusercontent.com/comfunnylj/telegram-market-feed/main/final_report.json
- https://raw.githubusercontent.com/comfunnylj/telegram-market-feed/main/daily_report.json
- https://raw.githubusercontent.com/comfunnylj/telegram-market-feed/main/top_issues.json

Telegram 데이터는 아이디어와 시장 관심도 파악의 1차 소스다. 외부 최신 사실·지수·가격·기업 뉴스는 웹 검색으로 추가 확인한다.

## 게시 전 필수 확인
1. 게시 시점의 S&P 500, NASDAQ, KOSPI 값을 신뢰할 수 있는 최신 소스로 확인한다.
2. 수치를 확인할 수 없으면 추정하거나 만들어내지 않는다.
3. 미국 시장이 닫혀 있으면 S&P 500과 NASDAQ은 가장 최근 정규장 종가와 등락률을 사용하고 그 기준을 자연스럽게 명시한다.
4. 오전 게시 시 KOSPI 개장 전이면 가장 최근 종가를 사용하고 '전일 종가'임을 표시한다. 장중이면 게시 시점에 가장 가까운 장중 값을 사용한다. 오후 게시 시에는 당일 종가를 우선한다.
5. Telegram에서 나온 중요한 기업·수치·사건은 웹으로 가능한 범위에서 교차확인한다.
6. 출처끼리 숫자가 다르면 보수적으로 표현하고 단정하지 않는다.

## 첫 글 요약과 지표 배치
- 첫 글은 캡처처럼 `MM/DD, 밤 사이 일어난 일`(아침), `MM/DD, 오늘 시장 한눈에`(저녁), `MM/DD, 에너지 시장 한눈에`(에너지) 제목으로 시작한다.
- 제목 다음에 `1. …\n2. …` 형식의 번호형 핵심 뉴스 요약을 한 줄 내외로 작성한다. 검증된 주요 뉴스 5~8개를 우선하되 유효 뉴스가 적으면 실제 건수만 쓴다. 수치·기업명·사건을 만들지 않는다.
- 요약 다음에 S&P 500·NASDAQ·KOSPI의 값, 등락률, 기준일/장중·종가 구분을 배치한다. 에너지 브리핑은 사용자 지정 WTI·브렌트유·두바이유를 같은 방식으로 표시한다.
- 첫 글 공간이 부족하면 지표와 상세를 다음 연결 글로 옮긴다. 요약이 맨 앞이라는 최신 사용자 지시가 기존 지표 최상단 규칙보다 우선한다.
- 대표 이미지는 첫 글에 붙이고 상세 해설은 다음 연결 글로 이어간다.

## 글쓰기 톤
- Threads 본문은 반말로 쓴다.
- 뉴스 앵커나 리서치센터 보고서처럼 딱딱하게 쓰지 않는다.
- 실제 투자자가 시장을 훑어보고 친구에게 설명하듯 자연스럽게 쓴다.
- 문단을 짧게 나누고 문단이 바뀔 때는 빈 줄을 충분히 둔다.
- 한 문단에 너무 많은 내용을 욱여넣지 않는다.
- 존댓말을 쓰지 않는다.
- AI, 인공지능이 작성했다는 표현, '샘플', 'AI 편집', 'AI 브리핑' 같은 표현을 본문과 이미지에 넣지 않는다.
- '더 재밌는 건', '재밌는 건', '정리하면', '한마디로', '핵심은', '여기서 중요한 건', '단순히 A가 아니라 B', '솔직히?', '결론적으로', '주목할 점은'처럼 AI 글에서 자주 반복되는 전환 문구를 피한다.
- '이건 꽤 흥미롭다', '눈여겨볼 만하다' 같은 상투적 평가를 남발하지 않는다.
- 매 문단을 동일한 길이와 구조로 맞추지 않는다.
- 지나치게 교훈적인 결론을 만들지 않는다.
- 이모지는 원칙적으로 쓰지 않거나 아주 적게 쓴다.
- 해시태그는 개별 글당 최대 1개만 사용한다.

## 전체 분량과 강제 분할
- 브리핑 전체는 기본 900~1,600자 수준으로 충분히 설명한다. 중요한 날은 더 길어도 된다. 같은 내용을 반복해 분량을 채우지 않는다.
- **오류 발생 여부와 관계없이 게시 호출 전에 모든 개별 글을 글자 수로 검증한다. 목표는 450자 이하, 절대 상한은 500자다.** 한글·영문·공백·개행·URL·번호·해시태그·추가 표기 모두 포함한다.
- 첫 요약 글과 모든 연결 글을 각각 검사한다. JavaScript에서는 완성된 각 `text`의 `length`(UTF-16)와 `Array.from(text).length`를 모두 확인해 보수적으로 450자 이하로 맞춘다. 검사 결과와 각 글 길이를 실행 기록에 남긴다.
- 분할은 문단→문장→절/공백 경계를 우선한다. 한 문단이 한도를 넘으면 그 문단 자체를 나눈다. URL·기업명·숫자·단위가 잘리지 않게 한다.
- 전체 내용을 삭제하거나 과도하게 줄여 한 글에 맞추지 않는다. 필요한 개수만큼 `descendants`로 연결한다. 2~3개 같은 고정 개수 제한을 두지 않는다.
- 분할 뒤 지표/출처/해시태그 등을 추가했으면 최종 본문으로 길이를 다시 검사한다. 한 개라도 상한을 넘으면 게시 호출 전에 다시 분할한다.
- 각 글의 해시태그는 최대 1개다.

## 기업명 노출
- 관련 기업을 자연스럽게 많이 언급한다.
- 기본적으로 8개 이상 기업/종목을 검토하고, 실제로 연결되는 경우 본문에 8~15개 정도를 자연스럽게 포함한다.
- 억지로 이름만 나열하지 말고 밸류체인·실적·수급·정책·경쟁 관계 안에서 연결한다.
- 국내와 해외를 적절히 섞는다.
- 예: 삼성전자, SK하이닉스, 마이크론, 엔비디아, 샌디스크, LG에너지솔루션, 삼성SDI, SK온, 알테오젠, MSD, 구글 등. 단, 실제 당일 데이터에 근거할 때만 사용한다.

## 콘텐츠 구조
고정 템플릿처럼 보이지 않게 매번 조금씩 바꾸되 대체로 다음 흐름을 따른다.
- 날짜 제목과 번호형 핵심 요약
- 검증된 지표 3개(공간 부족 시 다음 글)
- 오늘 시장 분위기를 자연스럽게 설명
- 미국 시장/매크로
- 반도체·AI 인프라 등 주요 산업
- 국내 시장/기업
- 당일 새로 부각된 개별 기업이나 테마
- 다음에 볼 포인트
- 해시태그

아침 글은 밤사이 미국장과 오전에 볼 국내 종목을 중심으로 한다.
저녁 글은 국내장 결과와 오후에 새로 나온 이슈, 다음 미국장 또는 다음 거래일에 볼 포인트를 중심으로 한다.
같은 날 아침 글과 저녁 글은 문장과 주요 논점을 최대한 중복하지 않는다.

## 이미지
브리핑 한 회당 대표 이미지 1장을 생성해 첫 글에 첨부한다.
- 세로형 4:5 비율을 기본으로 한다.
- 실제 금융 미디어가 만든 카드처럼 깔끔하고 정돈된 디자인을 사용한다.
- 본문의 가장 중요한 3개 이슈만 이미지에 넣는다.
- 본문을 이미지에 과도하게 복사하지 않는다.
- 'AI', '샘플', 'AI 편집', '본문 참고' 등의 문구를 넣지 않는다.
- 가짜 로고, 잘못된 기업명, 임의의 숫자, 임의의 지수값, 임의 차트 수치를 생성하지 않는다.
- 숫자를 넣을 경우 반드시 당일 확인된 소스의 정확한 숫자만 쓴다.
- 안전을 위해 시장 지수 수치는 원칙적으로 이미지가 아니라 요약 뒤 본문에 둔다.
- 이미지 안 한글이 깨지거나 틀리면 수정해서 사용한다.
- 가능하면 실제 기업 브랜드를 연상시키되 공식 로고를 부정확하게 재현하기보다 업종을 나타내는 시각 요소를 선호한다.

## 사실성
- 추측을 사실처럼 쓰지 않는다.
- Telegram의 단일 채널 주장만 있는 내용은 표현을 낮추거나 외부에서 확인한다.
- 복수 채널에서 확산된 내용은 시장 관심도가 높다는 근거로 활용할 수 있다.
- 투자 추천처럼 단정적으로 매수/매도 지시를 하지 않는다.
- 없는 숫자를 만들어내지 않는다.
- 숫자가 불확실하면 숫자를 빼고 서술한다.

## 중복 방지
- 같은 날 이미 게시한 핵심 사건을 그대로 반복하지 않는다.
- 오전 글의 주요 이슈가 오후에도 중요하면 새로운 정보·가격 반응·후속 뉴스가 생겼을 때만 다시 언급한다.
- 이전 게시물과 첫 문장, 결론, 기업 배열이 반복되지 않게 한다.

## 게시
Metricool 브랜드:
- blogId: 7283153
- Threads account: @genie_carrot
- timezone: Asia/Seoul

게시물은 autoPublish=true로 예약한다.
이미지 파일을 `mediaFiles`로 첨부한다. 실행 환경의 파일 업로드 방식에 맞춰 실제 값을 전달한다. **Codex Work에서 현재 Metricool 도구는 `mediaFiles`의 절대 로컬 파일 경로를 자동 업로드한다.** 생성 이미지가 로컬에 있으면 그 실제 경로를 전달한다. ChatGPT 첨부파일 ID를 직접 지원하는 환경에서만 반환된 실제 `file_...` ID를 사용한다. ID를 로컬 파일처럼 해석하며 `No such file or directory`가 발생하면 같은 ID를 재시도하지 말고 검수된 실제 이미지 경로로 업로드한다. ID가 없다는 이유만으로 로컬 이미지가 있는 게시를 중단하지 않는다. 임의 ID나 존재하지 않는 경로를 만들지 않는다.
- Metricool `createScheduledPost` 호출 시 최상위 인자는 `date`, `blogId`, `info`, `mediaFiles`를 사용한다. **`data` 인자를 보내지 않는다.**
- `info`는 객체가 아닌 **JSON 문자열(JSON.stringify 결과)**이어야 한다. 필수 구성: `autoPublish:true`, `draft:false`, `media:[]`, `providers:[{"network":"threads"}]`, `publicationDate:{"dateTime":"YYYY-MM-DDTHH:mm:ss","timezone":"Asia/Seoul"}`, `text`, `threadsData:{}`.
- 예: `createScheduledPost({date:"2026-10-09T10:30:00+09:00",blogId:"7283153",info:JSON.stringify({autoPublish:true,draft:false,media:[],providers:[{network:"threads"}],publicationDate:{dateTime:"2026-10-09T10:30:00",timezone:"Asia/Seoul"},text:body,threadsData:{}}),mediaFiles:[actualImagePathOrSupportedFileId]})` (예시 날짜는 실제 실행 시 미래 시각으로 교체).
- 성공 응답에서 게시물 `id`, `plannerUrl`, `autoPublish:true`, Threads 제공자 `PENDING`, 그리고 **비어 있지 않은 `media` URL**을 확인한다. 응답 확인 전에는 예약 성공으로 보고하지 않는다.
Threads provider만 사용한다.
게시 예정 시각이 이미 지났다면 가능한 가장 가까운 미래 시각으로 잡되 사용자에게 별도 확인을 요구하지 않는다.

## 실패 처리
- 최신 지수 세 개 중 하나라도 신뢰할 만한 값을 확보하지 못하면 게시하지 않고 사용자에게 실패 이유를 알린다.
- 이미지 생성에 실패하면 텍스트만 자동 게시하지 말고 게시를 중단한다.
- Metricool 게시 실패 시 같은 게시물을 무한 재시도하지 않는다.
- 데이터가 직전 게시와 사실상 동일하고 새로 쓸 내용이 부족하면 억지로 중복 글을 만들지 말고 해당 회차는 건너뛴다.


## Threads 발행 전 필수 검증
- 각 개별 글의 최종 길이와 번호형 요약·지표·출처·해석 구분을 확인한다. 해시태그는 개별 글당 최대 1개다.
- Metricool 공식 API `ScheduledPost.descendants`는 같은 `ScheduledPost` 객체 배열이다. 첫 글은 루트 `text`, 나머지는 `descendants`에 순서대로 넣는다. 각 글에 `text`, `providers:[{network:"threads"}]`, `publicationDate`, `autoPublish:true`, `draft:false`, `media:[]`, `threadsData:{}`를 넣는다. 정확한 최신 스키마는 https://app.metricool.com/api/swagger.json 에서 확인한다.
- Meta가 이미지 URL을 다운로드하여 미디어 컨테이너를 만든다. 공개 HTTPS 이미지 URL과 지원 규격을 확인한다. 업로드 완료·PENDING은 발행 성공이 아니다.
- 발행 후 첫 글 및 모든 연결 글의 `PUBLISHED`와 확인 가능한 실제 `publicUrl`을 확인해야 전체 성공이다. 실패·부분 성공은 구분한다.
- `ERROR`의 `detailedStatus`를 기록한다. `Media container not created by unknown cause`이면 이미지 재압축만 반복하지 말고 미디어 다운로드/컨테이너 생성 문제를 조사한다.
- 재시도 전에 실제 상태와 게시 이력을 확인한다. 이미 PUBLISHED인 동일 내용을 중복 게시하지 않는다.
